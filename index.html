01

Contexte du projet

BNA Corporate est une plateforme bancaire entreprise construite en monorepo Lerna. Elle regroupe deux applications — CSA (back-office administrateur) et eBanking (portail client)

02

Comment Claude a été intégré dans le workflow

Claude n'a pas remplacé le raisonnement du développeur — il l'a amplifié à chaque étape du cycle de développement, de la compréhension du besoin jusqu'à la revue de code post-implémentation.

1

Lecture & analyse de spec

Claude lit la User Story ClickUp en entier (prose + tableau Formulaire + wireframe), identifie les règles métier implicites et les gaps entre spec et maquette, puis génère un PRD structuré dans ai-docs/features/.

ClickUp MCP
2

Plan d'implémentation TDD

Avant d'écrire du code, Claude rédige les cas de test (tableau ID / Préconditions / Steps / Résultat attendu), identifie les hooks, utils, constants et pages à créer ou modifier, en respectant l'architecture existante.

TDD-first
3

Implémentation & revue

Claude génère l'implémentation minimale pour faire passer les tests (RED → GREEN), respecte les conventions CLAUDE.md (pas de module-level constants dans les hooks, export formatté pour les montants, optional chaining sur les données API), puis lance une revue automatique avant commit.

Code review skill

Exemples concrets de features développées

Les features ci-dessous illustrent la diversité des cas traités — du composant UI isolé au module complet avec routing, permissions et pagination.

eBanking · Dashboard

Opérations en attente — Vue globale des soldes

Accordion Pagination RBAC Month picker 14 TCs

Écran listant les opérations en attente par groupe/entreprise, avec navigation mensuelle, accordion collapsible et redirection contextuelle vers l'espace de l'entreprise concernée. Feature complète : PRD généré depuis la US ClickUp, 14 cas de test écrits en TDD, implémentation hook + utils + routing RBAC (RoutePermissionWrapper).

▸ Défi : grouper les opérations côté front (l'API renvoie un tableau plat), filtrer les entreprises sans opération, gérer le reset de page lors du changement de mois.
▸ Gain : Claude a tracé l'intégralité du plan (hooks, utils, sidebar entry, route guard, tests) en une session. Estimation manuelle : 4-5 jours. Réalisé en 1,5 jour.
▸ Qualité : couverture 14 TCs incluant cas limites (groupes vides, API error, pagination + changement de mois, permission manquante sur URL directe).
CSA + eBanking · Commandes

Commande de dinars & commande de devises — Feature from scratch

Nouveau module ebanking-ui / business / state Workflow CSA Jours fériés

Deux modules entièrement nouveaux côté eBanking (dinar-order et foreign-currency-order) : liste des demandes avec filtres, création de demande, confirmation, détail de la demande et commentaire d'approbation de la banque. Côté CSA, intégration du processus d'approbation et affichage du détail de la transaction dans transaction-context. La feature traverse toutes les couches : UI → Business → State.

▸ From scratch : Claude a posé la structure complète du module (service, types, constants, hooks, containers, pages, routes, locales, entrée sidebar) en suivant les conventions des modules existants.
▸ Réutilisation : le module devises a été construit sur le modèle du module dinars ; la logique de formatage des comptes a ensuite été extraite en fonctions réutilisables partagées par les deux.
▸ Règle métier : la date de retrait exclut les week-ends et jours fériés, via un composant weekday-date-input dédié et couvert par des tests.
▸ Sécurité : les pages de détail sont protégées par RoutePermissionWrapper.
eBanking · Comptes

Téléchargement AFB / MT94x — API v2

V2 Documents API File download Blob handler

Migration du téléchargement de fichiers AFB (relevés de compte) et MT94x de l'ancienne API vers le nouveau endpoint /secure/documents/v2. Gestion du blob, du nom de fichier extrait depuis l'en-tête Content-Disposition, et du fallback quand le format n'est pas disponible.

▸ Navigation cross-repo : Claude a tracé l'implémentation en lisant le backend BNA (bna-corp-backend/) pour confirmer le contrat du nouveau endpoint avant d'écrire une ligne de code front.
▸ Rule appliquée : exportAccessor sur les colonnes montant formaté via formatAmount, conformément à la règle CLAUDE.md ebanking-ui (Rule 5).
eBanking · Transferts

Virement groupé — Commission, annulation & permissions

Commission TVA Cancel flow Route permissions File upload

Série de features sur le module virement par fichier : affichage de la commission TVA sur le récapitulatif, flux d'annulation avec écran de confirmation, permission de route cancel-bulk-transfer, et gestion des fichiers dupliqués avec fallback de nom. Chaque sous-feature a été planifiée et livrée indépendamment.

▸ TDD : pour la commission, les tests ont d'abord vérifié le rendu de -- quand la donnée est absente, puis le format formatAmount quand elle est présente — avant l'implémentation.
▸ Règle optional chaining : commissionData?.commission au lieu de commissionData.commission — protège contre les champs renommés/absents en production sans attendre que le backend soit mis à jour.
eBanking · Dashboard

Panorama — Vérification & adaptation d'une feature existante

Existant Revue de code RoutePermissionWrapper Notifications

La page Panorama existait déjà dans le produit Bankerise Corporate. Le travail ne consistait pas à la réécrire, mais à vérifier son comportement sur le contexte BNA et à l'adapter : ajout de la section utilisateur, protection de la page par RoutePermissionWrapper, branchement des endpoints liste en attente et notifications, et intégration des opérations en attente avec traductions et routing.

▸ Vérification d'abord : Claude a lu l'implémentation existante (dashboard/features/panorama) et comparé son comportement à la US avant de proposer un changement — l'objectif était d'identifier les écarts, pas de tout réécrire.
▸ Adaptations ciblées : modifications limitées aux écarts constatés (section utilisateur, permissions de route, endpoints, locales, entrée sidebar), sans toucher au reste de la page.
eBanking · Transactions

Export CSV transactions — Montants formatés & devises zéro-décimal

formatAmount exportAccessor Zero-decimal Excel-safe dates

Export de l'historique de transactions en CSV avec gestion des montants formatés (ne pas laisser Excel afficher ####### sur les dates), préservation des devises à zéro décimal, et exportAccessor cohérent avec le rendu visuel de chaque colonne.

▸ Règle critique : Rule 5 impose que l'exportAccessor appelle formatAmount — la même fonction que le rendu visuel. Claude a appliqué cette règle et corrigé les colonnes existantes qui ne le faisaient pas encore.
▸ Edge case : les devises zéro-décimal (pas de centimes) étaient incorrectement filtrées. Identifié et corrigé lors de l'écriture du test avant implémentation.
04

Gains en temps et en qualité

◎ Gain de temps par activité

Ce qui va plus vite avec Claude, comparé à la façon habituelle de travailler sur des features de complexité comparable.

▸ Lecture & analyse de spec : Claude lit la US complète (prose, tableaux, règles de gestion) et en sort une synthèse claire avec les points ambigus. On ne relit plus la spec plusieurs fois pour comprendre ce qui est demandé.
▸ Génération des cas de test : les cas de test sont proposés directement à partir de la spec, y compris les cas limites. Il reste seulement à les relire et à les compléter, au lieu de les écrire un par un.
▸ Implémentation : la structure d'un module (service, types, hooks, containers, pages, routes, locales) est posée rapidement en suivant les modules existants. Le temps est consacré à la logique métier plutôt qu'au code répétitif.
▸ Navigation cross-repo / cross-package : retrouver où une donnée est définie, transformée et affichée à travers UI, Business, State et le backend se fait en une question, sans parcourir les dossiers à la main.
▸ Debugging : Claude remonte la chaîne d'appel pour trouver la cause réelle d'un bug avant de proposer un correctif, ce qui évite les essais au hasard.
▸ Documentation (PRD, plans) : le PRD et le plan d'implémentation sont rédigés à partir de la US et du code. Il ne reste qu'à les valider et à les ajuster.

◎ Amélioration de la qualité

L'impact le plus fort n'est pas la vitesse seule — c'est la réduction des aller-retours en revue et la cohérence des conventions sur l'ensemble du projet.

▸ Tests plus complets : les tests sont écrits avant l'implémentation (TDD), et chaque feature arrive avec ses tests au lieu de les ajouter après coup.
▸ Respect des conventions : les règles du CLAUDE.md (structure page/container, nommage anglais, formatAmount, optional chaining…) sont appliquées systématiquement, sur chaque fichier.
▸ Bugs détectés plus tôt : beaucoup de problèmes (donnée absente, cas d'erreur API, permission manquante) sont repérés pendant l'écriture des tests, avant même la code review.
▸ Moins d'aller-retours en review : le code soumis respecte déjà les conventions et couvre les cas limites, donc les retours de revue portent sur le fond plutôt que sur la forme.
▸ Cohérence du naming et de la structure : les nouveaux modules ressemblent aux modules existants, ce qui rend le code plus facile à lire et à maintenir par toute l'équipe.
▸ Edge cases couverts : les cas que la spec ne mentionne pas explicitement (listes vides, champs absents, jours fériés…) sont signalés et traités au lieu d'être découverts en recette.
05

Ce qui a le mieux fonctionné

Quatre pratiques ont fait la différence au quotidien. Chacune répond à un problème concret du projet et produit un résultat visible dans le code livré.

Pratique 01

Mémoire de projet persistante

Problème : sur un monorepo multi-package, les conventions sont nombreuses et faciles à oublier d'une feature à l'autre.

Avec Claude : les règles du projet (CLAUDE.md + fichiers memory/) sont conservées entre les sessions et appliquées sans rappel — optional chaining, pas de constantes au niveau module, export formaté.

// Appliqué automatiquement : data?.field ?? '--' // optional chaining // et non : data.field

RésultatDes conventions identiques sur toutes les features, sans relecture dédiée.

Pratique 02

Détection des contraintes cachées

Problème : dans les US ClickUp, certaines contraintes n'apparaissent que dans les tableaux Formulaire ou les wireframes, pas dans le texte.

Avec Claude : la spec est lue en entier au format text/md ; les écarts entre texte, tableaux et maquette sont listés et documentés avant de coder.

RésultatMoins de corrections après review : les ambiguïtés sont levées avant l'implémentation.

Pratique 03

Navigation cross-repo précise

Problème : le monorepo consomme des packages compilés (@corporate/*) dont la source se trouve dans un repo voisin.

Avec Claude : la source réelle est lue directement, sans passer par le dist — y compris le backend pour confirmer un contrat d'API.

RésultatPas de conclusions erronées sur des types ou des comportements « manquants ».

Pratique 04

TDD systématique

Problème : les cas limites sont souvent découverts tard, en recette ou en production.

Avec Claude : les cas de test sont rédigés en tableau avant la moindre ligne d'implémentation, ce qui oblige à penser aux edge cases dès le départ.

// TC-08 : échec du changement de workspace // → modal d'erreur, l'utilisateur reste sur l'écran // Détecté avant l'implémentation du hook

RésultatLes bugs sont trouvés en phase RED, pas en revue ni en production.

Conclusion

Claude comme amplificateur de rigueur, pas de productivité brute

Le gain le plus mesurable n'est pas la vitesse d'écriture du code, mais la réduction de la dette invisible : ces petits écarts qui ne cassent rien sur le moment et qui coûtent cher en review, en recette ou en production. Sur un projet bancaire de cette complexité — monorepo multi-package, deux applications, règles métier strictes, specs réparties entre texte, tableaux et maquettes — c'est là que Claude a le plus apporté.

Specs mal lues

Chaque US est lue en entier, tableaux Formulaire et wireframes compris. Les contraintes cachées sont relevées avant de coder.

Edge cases non couverts

Les cas de test sont écrits avant l'implémentation. Données absentes, erreurs API et permissions manquantes sont traitées dès le départ.

Conventions à géométrie variable

Les règles du CLAUDE.md sont appliquées de la même façon sur chaque feature, quel que soit le module ou le package.

Claude a fonctionné comme un co-développeur rigoureux : il propose, vérifie et signale ; le développeur garde la main sur les choix d'architecture, la validation métier et la décision finale.
