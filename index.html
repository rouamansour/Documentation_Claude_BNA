01

Contexte du projet

BNA Corporate est une plateforme bancaire entreprise construite en monorepo. Elle regroupe deux applications — CSA (back-office administrateur) et eBanking (portail client)

02

Comment Claude a été intégré dans le workflow

Claude n'a pas remplacé le raisonnement du développeur — il l'a amplifié à chaque étape du cycle de développement, de la compréhension du besoin jusqu'à la revue de code post-implémentation.

1

Lecture & analyse de spec

Claude lit la User Story ClickUp en entier (tableau Formulaire + wireframe), identifie les règles métier implicites et les gaps entre spec et maquette, puis génère un PRD structuré dans ai-docs/features/.

ClickUp MCP
2

Plan d'implémentation TDD

Avant d'écrire du code, Claude rédige les cas de test (tableau ID / Préconditions / Steps / Résultat attendu), identifie les hooks, utils, constants et pages à créer ou modifier, en respectant l'architecture existante.

TDD-first
3

Implémentation & revue

Claude génère l'implémentation minimale pour faire passer les tests (RED → GREEN), respecte les conventions du projet définies dans CLAUDE.md, puis effectue automatiquement une revue du code avant le commit.

Code review skill

Exemples concrets de features développées

Les features ci-dessous illustrent la diversité des cas traités — du composant UI isolé au module complet avec routing, permissions et pagination.

eBanking · Dashboard

Opérations en attente — Vue globale des soldes

Accordion Pagination RBAC Month picker

Écran listant les opérations en attente par groupe/entreprise, avec navigation mensuelle, accordion collapsible et redirection contextuelle vers l'espace de l'entreprise concernée. Feature complète : PRD généré depuis la US ClickUp, 14 cas de test écrits en TDD, implémentation hook + utils + routing RBAC (RoutePermissionWrapper).

▸ Défi : grouper les opérations côté front (l'API renvoie un tableau plat), filtrer les entreprises sans opération, gérer le reset de page lors du changement de mois.
▸ Gain : Claude a tracé l'intégralité du plan (hooks, utils, sidebar entry, route guard, tests) en une session. L’estimation manuelle prévoyait une charge importante, tandis que l’utilisation de Claude a permis une réalisation beaucoup plus rapide.
▸ Qualité : couverture 14 TCs incluant cas limites (groupes vides, API error, pagination + changement de mois, permission manquante sur URL directe).
CSA + eBanking · Commandes

Commande de dinars & commande de devises — Feature from scratch

Nouveau module ebanking-ui / business / state Workflow CSA Jours fériés

Deux modules entièrement nouveaux côté eBanking (dinar-order et foreign-currency-order) : liste des demandes avec filtres, création de demande, confirmation, détail de la demande et commentaire d'approbation de la banque. Côté CSA, intégration du processus d'approbation et affichage du détail de la transaction dans transaction-context. La feature traverse toutes les couches : UI → Business → State.

▸ Défi : construire deux modules sans base existante, traversant toutes les couches (UI → Business → State) et les deux applications (eBanking pour la demande, CSA pour l'approbation) ; respecter la règle métier de la date de retrait (hors week-ends et jours fériés) ; éviter de dupliquer la logique entre deux modules très proches.
▸ Gain : Claude a posé la structure complète du module (service, types, constants, hooks, containers, pages, routes, locales, entrée sidebar) en suivant les conventions des modules existants. Le module devises a ensuite été construit sur le modèle du module dinars, ce qui a fortement réduit le temps de mise en place du second module.
▸ Qualité : la logique de formatage des comptes a été extraite en fonctions réutilisables partagées par les deux modules ; la règle des jours ouvrés est isolée dans un composant weekday-date-input dédié et couvert par des tests ; les pages de détail sont protégées par RoutePermissionWrapper.
eBanking · Transferts

Virement local — Simple, permanent & multiple

Module existant Commission & TVA Cancel flow Permissions Config des champs

Évolutions sur le module virement local déjà existant, pour ses trois variantes (simple, permanent, multiple) : affichage des commissions et de la TVA sur le récapitulatif, ajout de la feature d'annulation avec écran de confirmation, ajout des permissions sur les actions et les routes, et configuration des champs du formulaire.

▸ Défi : modifier un module existant sans casser les parcours en place ; appliquer les évolutions de façon cohérente sur les trois types de virement, qui partagent une partie de la logique mais ont chacun leurs spécificités ; gérer les commissions et la TVA lorsque la donnée est absente ou incomplète côté API.
▸ Gain : Claude a rapidement cartographié le module existant (composants, hooks, services, routes) et identifié les points d'impact pour chaque variante avant toute modification. Chaque évolution (commission/TVA, annulation, permissions, configuration des champs) a été planifiée et livrée indépendamment.
▸ Qualité : tests écrits avant l'implémentation (affichage de -- quand la commission est absente, format formatAmount quand elle est présente) ; accès défensif aux données via optional chaining (commissionData?.commission) ; actions et routes protégées par permission ; conventions du module existant respectées.
eBanking · Dashboard

Panorama — Vérification & adaptation d'une feature existante

Existant Revue de code RoutePermissionWrapper Notifications

La page Panorama existait déjà dans le produit Bankerise Corporate. Le travail ne consistait pas à la réécrire, mais à vérifier son comportement sur le contexte BNA et à l'adapter : ajout de la section utilisateur, protection de la page par RoutePermissionWrapper, branchement des endpoints liste en attente et notifications, et intégration des opérations en attente avec traductions et routing.

▸ Défi : adapter une page produit existante au contexte BNA sans la réécrire ni casser son comportement d'origine ; identifier précisément les écarts entre l'implémentation produit et la US BNA ; brancher de nouveaux endpoints (liste en attente, notifications) dans une page déjà structurée.
▸ Gain : Claude a lu l'implémentation existante (dashboard/features/panorama) et l'a comparée à la US avant toute modification, ce qui a permis d'obtenir rapidement la liste des écarts à traiter au lieu d'analyser la page manuellement. Le travail s'est ensuite limité à ces écarts.
▸ Qualité : modifications ciblées (section utilisateur, permissions de route, endpoints, locales, entrée sidebar) sans toucher au reste de la page ; accès protégé par RoutePermissionWrapper ; opérations en attente intégrées avec traductions et routing cohérents avec le reste de l'application.
04

Gains en temps et en qualité

◎ Gain de temps par activité

Ce qui va plus vite avec Claude, comparé à la façon habituelle de travailler sur des features de complexité comparable.

▸ Lecture & analyse de spec : Claude lit la US complète (tableaux, règles de gestion) et en sort une synthèse claire avec les points ambigus. On ne relit plus la spec plusieurs fois pour comprendre ce qui est demandé.
▸ Génération des cas de test : les cas de test sont proposés directement à partir de la spec, y compris les cas limites. Il reste seulement à les relire et à les compléter, au lieu de les écrire un par un.
▸ Implémentation : la structure d'un module (service, types, hooks, containers, pages, routes, locales) est posée rapidement en suivant les modules existants. Le temps est consacré à la logique métier plutôt qu'au code répétitif.
▸ Navigation cross-repo / cross-package : retrouver où une donnée est définie, transformée et affichée à travers UI, Business, State et le backend se fait en une question, sans parcourir les dossiers à la main.
▸ Debugging : Claude remonte la chaîne d'appel pour trouver la cause réelle d'un bug avant de proposer un correctif, ce qui évite les essais au hasard.
▸ Documentation (PRD, plans) : le PRD et le plan d'implémentation sont rédigés à partir de la US et du code. Il ne reste qu'à les valider et à les ajuster.

◎ Amélioration de la qualité

L'impact le plus fort n'est pas la vitesse seule — c'est la réduction des aller-retours en revue et la cohérence des conventions sur l'ensemble du projet.

▸ Tests plus complets : les tests sont écrits avant l'implémentation (TDD), et chaque feature arrive avec ses tests au lieu de les ajouter après coup.
▸ Respect des conventions : les règles du CLAUDE.md (structure page/container, nommage anglais, formatAmount...) sont appliquées systématiquement, sur chaque fichier.
▸ Bugs détectés plus tôt : beaucoup de problèmes (donnée absente, cas d'erreur API, permission manquante) sont repérés pendant l'écriture des tests, avant même la code review.
▸ Moins d'aller-retours en review : le code soumis respecte déjà les conventions et couvre les cas limites, donc les retours de revue portent sur le fond plutôt que sur la forme.
▸ Cohérence du naming et de la structure : les nouveaux modules ressemblent aux modules existants, ce qui rend le code plus facile à lire et à maintenir par toute l'équipe.
▸ Cas limites couverts : Claude anticipe les situations non prévues dans la spec et les traite dès le développement, réduisant ainsi les problèmes détectés en recette.

05

Ce qui a le mieux fonctionné

Quatre pratiques ont fait la différence au quotidien. Chacune répond à un problème concret du projet et produit un résultat visible dans le code livré.

Pratique 01

Réutiliser un module existant comme modèle

Problème : quand deux features se ressemblent (commande de dinars et commande de devises), les coder séparément double le travail et crée deux versions d'une même logique, qui finissent par diverger.

Avec Claude : le module dinars, une fois terminé, sert de modèle. Claude reprend sa structure pour créer le module devises, ne modifie que ce qui change, puis extrait la logique commune dans des fonctions partagées par les deux modules.

// dinar-order → module de référence // foreign-currency-order → même structure, adaptée aux devises // Formatage des comptes → fonctions partagées par les deux

RésultatLe second module est livré plus vite, et une correction faite dans la logique commune s'applique aux deux.

Pratique 02

Détection des contraintes cachées

Problème : dans une US ClickUp, une règle peut être absente du texte et n'apparaître que dans le tableau Formulaire ou sur la maquette. Si on ne lit que le texte, la règle est oubliée et le bug n'est découvert qu'en recette.

Avec Claude : l'US est lue en entier (texte, tableaux et maquettes) et Claude liste chaque écart entre ces sources avant d'écrire du code. Par exemple, pour la commande de dinars :

// Écart repéré avant implémentation Texte de l'US : « choisir une date de retrait » Règle métier : pas de week-end ni de jour férié → composant weekday-date-input dédié + tests

RésultatLes règles cachées sont repérées dès le départ, au lieu d'être découvertes en recette.

Pratique 03

Navigation cross-repo précise

Problème : Le frontend utilise des packages compilés (@corporate/*), alors que leur code source se trouve dans d’autres repositories. Se baser uniquement sur le dist peut donner une vision incomplète ou incorrecte des types, des fonctionnalités et des comportements.

Avec Claude : Claude identifie et consulte directement les repositories sources des packages utilisés. Il peut également vérifier le backend pour confirmer les contrats d’API, les paramètres et les réponses attendues.

RésultatUne compréhension plus fiable du fonctionnement réel de l’application et moins de risques de conclure à tort qu’un type, un champ ou un comportement est absent ou non supporté.

Pratique 04

TDD systématique

Problème : les cas limites sont souvent découverts tard, en recette ou en production.

Avec Claude : les cas de test sont rédigés en tableau avant la moindre ligne d'implémentation, ce qui oblige à penser aux edge cases dès le départ.

// TC-08 : échec du changement de workspace // → modal d'erreur, l'utilisateur reste sur l'écran // Détecté avant l'implémentation du hook

RésultatLes bugs sont trouvés en phase RED, pas en revue ni en production.

Conclusion

Claude comme amplificateur de rigueur, pas de productivité brute

Le principal apport de Claude n’est pas seulement de développer plus rapidement, mais surtout d’anticiper les petits écarts et oublis avant qu’ils ne deviennent des problèmes en review, en recette ou en production. Cet apport est particulièrement important sur un projet bancaire complexe avec plusieurs packages, applications, règles métier et sources de spécifications.

Specs mal lues

Chaque US est lue en entier, tableaux Formulaire et wireframes compris. Les contraintes cachées sont relevées avant de coder.

Gestion des cas limites

Les cas de test sont écrits avant l'implémentation. Données absentes, erreurs API et permissions manquantes sont traitées dès le départ.

Conventions uniformes

Les règles définies dans CLAUDE.md sont appliquées de manière cohérente à toutes les fonctionnalités, quel que soit le module ou le package concerné.

Claude a fonctionné comme un co-développeur rigoureux : il propose, vérifie et signale ; le développeur garde la main sur les choix d'architecture, la validation métier et la décision finale.

« La valeur n'est pas dans la génération de code — elle est dans la cohérence maintenue au fil des features et sur la durée du développement. »
